It intentionally avoids duplicating volatile product details, PR status and exact SHAs. Those belong in live GitHub, `ACTIVE_CHAT_HANDOFF.md`, `ARAR_BULURUZ_CURRENT_STATE.md` and `PRODUCT_CONTRACT_V2.md`.

## Mandatory start

Before a material project answer or repository mutation:

1. read `../AGENTS.md`;
2. read `AI_OPERATING_MODEL_V2.md`;
3. read `ACTIVE_CHAT_HANDOFF.md`;
4. verify live GitHub `main`, active PR/branch/exact SHA and relevant workflows;
5. read `ARAR_BULURUZ_CURRENT_STATE.md`;
6. read `PRODUCT_CONTRACT_V2.md`;
7. read the decision log/backlog and task-specific technical evidence as needed;
8. identify the active writer before any mutation.

## Persistent roles

- **Founder:** final consequential product, budget, production, real-data and risk-acceptance decisions.
- **Main Execution Chat:** default implementation/debug/CI/docs owner.
- **Advisor Chat:** prioritization, REDTEAM, materiality, independent verification and specialist routing.
- **Codex:** budgeted specialist engineer for difficult code/security/migration/debugging.
- **Work:** budgeted independent research/review for consequential decisions.
- **Lovable:** frontend/UX implementation specialist; not backend/security/production owner.

Room numbers are temporary; roles persist.

## One-writer rule

Only one repository/code writer owns the same active implementation scope at a time.

Before switching writers, preserve:

- branch and exact SHA;
- committed changes;
- test/workflow state;
- remaining work;
- forbidden scope.

Read-only independent review may happen in parallel.

## Hard gates

Repository readiness does not authorize live operation.

Unless explicitly opened by the founder, keep closed:

- real personal/seller data;
- production backend/runtime activation;
- production secrets/environment changes;
- paid recurring infrastructure/services;
- real SMS;
- production EİDS;
- Ads/monetization;
- payments/orders/reservations/commission;
- Tarladan changes;
- force-push/history rewrite.

Current tax/company sequencing does not override these gates. Read the latest decision log for the active GVK Mükerrer 20/B / company formalization decision.

## Specialist routing

Use the minimum-cost capable owner.

For consequential, uncertain, costly or difficult-to-reverse choices, consider Work as an independent second opinion when it materially reduces decision risk.

When free/expiring Lovable credits are available, actively look for bounded high-value user-visible frontend/UX work rather than allowing useful credits to expire. Do not force backend/security/test-infrastructure work into Lovable merely to spend credits.

## Chat rollover

When a Main Execution or Advisor room fills:

1. write durable truth to GitHub;
2. update `ACTIVE_CHAT_HANDOFF.md`;
3. record exact live state and immediate next action;
4. record recent founder decisions that supersede old assumptions;
5. identify the active writer;
6. start the new room by re-verifying live GitHub.

## Knowledge write-back

- durable operating principle → operating model / project memory;
- current technical/runtime state → current state;
- current room continuity → active handoff;
- consequential founder choice → decision log;
- open/deferred work → backlog;
- current consumer contract → product contract;
- dated test/review evidence → dated evidence file where useful.

Do not store passwords, tokens, private customer records or unnecessary personal data in repository documentation.
